### Тема: ISP & DIP: рефакторинг і DI через конструктор

### Мета роботи: Застосувати принципи розділення інтерфейсу (ISP) та інверсії залежностей (DIP) для рефакторингу існуючого коду, а також реалізувати Dependency Injection (DI) через конструктор для зменшення зв’язаності та покращення тестування.

## 2. Аналіз порушень
### 2.1 Порушення DIP (Dependency Inversion Principle)

Принцип DIP говорить:
Модулі верхнього рівня не повинні залежати від модулів нижнього рівня. Обидва повинні залежати від абстракцій.

Порушення:

UserAccountManager напряму створює:
- DatabaseConnection
- SmtpClient
- SmsGateway

Відсутні інтерфейси.

Неможливо легко замінити реалізацію (наприклад, для тестування).

Наслідки:
- Жорстка зв’язаність (tight coupling).
- Складність модульного тестування.
- Неможливість легко змінити спосіб збереження або відправки повідомлень.

## 2.2 Порушення ISP (Interface Segregation Principle)

Принцип ISP говорить:
Клієнт не повинен залежати від методів, які він не використовує.

У початковій реалізації:
Відсутні інтерфейси.
У разі створення одного великого інтерфейсу (наприклад IUserService) він містив би:

- Register
- Login
- SendEmail
- SendSms

Це змусило б деякі класи реалізовувати зайві методи.

## 4. Висновки

### Під час виконання лабораторної роботи було:

Проаналізовано порушення принципів ISP та DIP.
- Виявлено жорстку залежність класу UserAccountManager від конкретних реалізацій служб.
- Виділено вузькоспеціалізовані інтерфейси.
- Реалізовано Dependency Injection через конструктор.
- Зменшено зв’язаність між компонентами системи.
- Покращено гнучкість та тестованість коду.

У результаті рефакторингу система стала:
- більш масштабованою,
- простішою для модифікації,
- готовою до модульного тестування,
- архітектурно правильною відповідно до принципів SOLID.
